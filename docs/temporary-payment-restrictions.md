# Временные ограничения на оплату долгов (до фикса round 3)

Статус: **активно, добавлено 2026-08-20** перед деплоем в прод текущей версии (round 1 + round 2
из `docs/known-issue-payment-clamp-residual.md`). Уберётся целиком, когда будет реализован round 3
(`docs/payments-logic-migration.md` — миграция на `payment_game_shares`, даёт полностью безопасный
расчёт для любой комбинации игр без всех ограничений ниже).

Этот док — самостоятельный, не требует чтения остальных двух доков, чтобы понять, что убирать и
как — специально, чтобы не пришлось собирать контекст заново перед уборкой.

## Зачем

Round 1 (`js/history.js`) чинит клампинг математически корректно, но не идеально гибко: как только
несколько игр объединены одним платежом, оплатить их порознь после этого нельзя (можно только
смотреть/считать — см. round 2). Перед тем как выкатить это в прод, решили добавить дополнительный,
более консервативный запас прочности на **оплату** конкретно — три независимых временных ограничения,
пока round 3 не даст полностью гибкий и точный расчёт для любой выборки игр.

Все три ограничения блокируют **только оплату** (кнопку «✓ Оплатил» и сам вызов `settleDebt()`).
Просмотр игр, выбор чекбоксов, расчёт долгов — всё это работает как обычно, без ограничений.

## Что именно ограничено

Весь код — один непрерывный блок в начале `js/history.js` (строки 6-38 на момент написания:
константы + `parseGameDateStr()` + `getTemporarySettleBlockReasons()`), плюс два места, где он
используется:

1. **Дата отсечки — 01.07.2026.** Если в выборке есть хотя бы одна игра с `date_str` раньше этой
   даты — оплата блокируется. Дата парсится из `games.date_str` (формат `DD.MM.YYYY HH:MM`,
   подтверждён одинаковым на всех 49 реальных играх в проде на момент написания) через
   `parseGameDateStr()`. Специально не используется `games.created_at` — она может расходиться с
   реальной датой игры на несколько дней (найдено на реальных данных: игры 85/86 добавлены в
   приложение через 3 дня после самой игры). Непарсящаяся дата = блокировка (fail-closed).
2. **Не больше 3 игр одновременно.** `selectedIds.length > 3` блокирует оплату. Не ограничивает
   сам выбор чекбоксов и кнопки «Выбрать все открытые игры»/«Выбрать группу» — только фактическую
   оплату. Все 4 реально существующие связанные группы в проде (27+28+29, 44, 46, 51+52+53) — ровно
   по 3 игры, так что это ограничение не мешает закрыть ни одну из них целиком.
3. **Сумма транзакции > 300₽.** Если хотя бы одна транзакция в списке долгов больше 300₽ —
   блокируется **весь** список (не только эта конкретная транзакция) — так же, как round 2
   блокирует весь список целиком при пропущенном платеже (жадный алгоритм `minimizeTransactions()`
   может исказить любую пару в списке, а не только связанную с проблемной суммой).

Место применения:
- `_doUpdateDebts()` (`js/history.js`, около строки 429-434): `blockSettle` теперь = пропущенный
  платёж ИЛИ хотя бы одна из трёх причин выше; рендерится отдельная спокойная заметка
  `⏳ Оплата временно недоступна: <причины>.` (специально не `⚠️` — по просьбе не пугать
  пользователей).
- `settleDebt()` (`js/history.js`, около строки 475): защитная проверка на входе, дублирует ту же
  логику — на случай, если состояние UI почему-то разойдётся с реальным (кнопка задизейблена, но
  вдруг вызов случился напрямую).

## Что НЕ добавлено (сознательно)

Обсуждали и отклонили отдельное предупреждение вида «оплата широкой группы заблокирует оплату по
более узкой выборке позже» — решили не пугать пользователей лишним текстом; существующей реактивной
заметки round 2 (`🔗 Без игр … расчёт неполный — оплата долгов ниже заблокирована`) достаточно.

## Как убрать после реализации round 3

1. `js/history.js`: удалить весь блок между `// ===== TEMPORARY SETTLE GATES ... =====` и
   `// ===== END TEMPORARY SETTLE GATES =====` (константы + `parseGameDateStr()` +
   `getTemporarySettleBlockReasons()`).
2. `js/history.js`, `_doUpdateDebts()`: убрать строки, вычисляющие `legacyBlockReasons`/`legacyNote`,
   вернуть `blockSettle` к `skippedPayments.length > 0` (или убрать вовсе, если round 3 вообще
   снимает необходимость в `blockSettle`/`skippedPayments` — см. `payments-logic-migration.md`).
3. `js/history.js`, `settleDebt()`: убрать защитную проверку в начале функции.
4. Удалить `tests/scenarios/08-temporary-settle-gates.test.js` и его строку в `tests/run-all.js`.
5. Убрать соответствующий пункт из `TODO.md`.
6. Удалить этот файл (`docs/temporary-payment-restrictions.md`) и cross-reference на него в
   `docs/payments-logic-migration.md`.

## Влияние на будущую реализацию round 3

Не усложняет ни код, ни бэкафилл. Подробности — в `docs/payments-logic-migration.md` (раздел про
эти временные гейты), коротко: гейты — чисто UI-слой поверх существующего расчёта, не трогают
`computeRemainingDebt()`/схему `payments`; новые платежи, созданные за время действия ограничений —
обычные строки в той же таблице `payments`, бэкафилл обработает их точно так же, как исторические,
без специальной обработки (и даже проще — суммы и число игр в них заведомо меньше).
